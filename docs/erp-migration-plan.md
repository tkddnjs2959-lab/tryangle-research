# TRYANGLE ERP 데이터 이행 계획

작성 기준: 2026-11-25. 범위는 3단계 3.3의 **검토용 이행 명세**다. [업무 계약 초안](erp-domain-contract.md)의 권장 원칙을 채택한다. 운영 DB, 코드, 배포에는 이 계획을 적용하지 않았다.

## 채택한 기준

- 신규 매체연기 수강 등록은 `coaching_students.id`를 학생 식별자로 필수 참조한다. 재등록은 새 등록 행으로 만들고 이전 기간의 가격·상태를 보존한다.
- 청구, 수납, 배분을 분리한다. 환불과 정정은 원거래를 참조하는 후속 거래로 보존한다.
- 포지셔닝은 신규 운영하지 않으며 기존 배우·리서치 기록만 보존한다. 포지셔닝 배우를 매체연기 학생으로 자동 전환하거나 기존 두 원장의 정보를 자동 병합하지 않는다.
- `enrollments`의 기존 1건은 분류와 연결을 확인하기 전 수정하지 않는다. `payments` 및 `checkout_orders`는 현재 0건이므로 기존 결제 이력 마이그레이션을 가정하지 않는다.
- Sheets는 마감된 월의 합계 대사 전용이며 Supabase의 거래 원장을 갱신하지 않는다.

## 적용 단위와 순서

| 순서 | 변경안(모두 추가형) | 적용 전에 확인할 조건 | 되돌리기 경로 |
|---|---|---|---|
| M0 기준선 | 운영 스키마, 제약, 인덱스, 테이블별 건수, 실제 쓰기 경로와 코드 배포 버전을 기록. 마이그레이션 이력과 저장소 파일을 대조 | 저장소에 `enrollments`·`payments`·`checkout_orders` 생성 SQL이 없으므로 운영 정의의 출처 확인 | 변경 없음 |
| M1 학생 연결 | `coaching_students.id`를 매체연기 학생 식별자로 사용. 등록에 nullable `student_id` FK를 추가하고 학생 입력 화면에서 새 등록에만 필수 적용 | 기존 등록 1건의 소유자와 매체연기 학생과의 관계 수동 검토; 이름/연락처 자동 조인 금지 | 새 입력 경로 비활성화. 기존 코칭 학생 정보와 등록의 기존 FK는 유지 |
| M2 상품·계약 | 상품/가격 기준정보를 별도 보관하고 `enrollments`에 계약 당시의 상품명, 수강 빈도, 금액, 시작/종료일 스냅샷을 보강. 새 등록에 필수 입력을 서버에서 강제 | 상품별 기간·중도 합류·취소 정책 결정 | 기존 화면 경로로 복귀. 추가 필드는 보존 |
| M3 청구·수납 | 청구 항목, 수납 이벤트, 배분, 원거래를 가리키는 환불/정정 기록, 중복 방지 키를 추가. `payments`와의 관계를 확인한 후 신규 원장 단일 쓰기 경로 선택 | `payments`의 기존 의미와 외부 쓰기 주체 확정. 결제 공급자 이벤트 검증 방법 결정 | 신규 쓰기 차단 및 검증된 거래를 보존. 회계 원장 행은 삭제하지 않음 |
| M4 권한·감사 | 작업별 역할/허용 작업 정의, 재무 거래와 감사 기록을 같은 트랜잭션으로 묶는 DB 함수 또는 동등한 원자 경로 추가 | 기존 `requireAdmin`과 service role 사용 경로의 권한 적용 범위 점검 | 기능 플래그로 새 쓰기 차단. 감사 이력 보존 |
| M5 마감 | 업무 기간, 집계 버전, 확정 스냅샷 및 원천 쓰기 잠금 도입. 확정/재개방은 승인 사유와 버전을 기록 | 선결제·환불·정산 귀속 정책과 월마감 승인자 확정 | 잘못된 확정은 승인 절차로 재개방/재확정. 이력 삭제 금지 |
| M6 Sheets | 마감 버전별 내보내기 실행 ID, 합계·건수·상태를 기록하고 월 합계만 보낸다 | Sheets의 확정 양식과 대사 항목 확정 | 내보내기 중지·재시도. Supabase 확정본은 유지 |

**범위:** 사용자의 결정에 따라 신규 ERP는 매체연기만 다룬다. 기존 포지셔닝 자료는 이행 대상에서 제외하며 삭제하지 않는다. 상담 문의에서 매체연기로 등록하는 경우에는 관리자가 명시적으로 코칭 학생을 만들거나 연결한다.

## 데이터 이행·검증 규칙

1. 새 컬럼은 우선 nullable로 추가한다. 기존 행에 임의 ID, 기본 가격, 완료 상태를 일괄 대입하지 않는다.
2. 기존 등록 1건은 ID와 현재 FK만 보존한 채 관리자 검토 대기 목록에 둔다. 연결 대상이 확인될 때만 학생 ID를 지정하고 관리자·시각·근거를 남긴다.
3. 새 등록은 화면·서버에서 학생 ID 필수, 유효한 기간/가격, 중복 방지 키를 요구한다. 구버전 서버가 병행하는 동안에는 DB의 전체 `NOT NULL` 전환을 서두르지 않는다.
4. 읽기 화면은 구 경로와 신 경로의 건수/합계를 같은 월·상태 범위로 대조한 후 전환한다. 결제 기록이 0건인 지금은 환불·부분수납 시나리오를 운영 데이터로 검증할 수 없으므로 비식별 시범 데이터에서 확인한다.
5. 모든 결제 주문의 공급자 이벤트는 검증된 고유 키와 함께 처리한다. 같은 이벤트 재시도는 기존 결과를 반환해야 하며 청구 배분 총액이 확정 수납액을 넘을 수 없다.
6. 마감 시점에는 월별 청구, 수납, 조정, 비용의 건수·금액과 집계 로직 버전을 함께 보존한다. 확정 뒤 과거 원천 행의 삭제/덮어쓰기는 모든 쓰기 경로에서 차단한다.

## 검증 게이트

| 게이트 | 확인 내용 | 통과 기준 |
|---|---|---|
| G1 구조 | 운영 마이그레이션 출처, 기존 FK/RLS/권한과 새 객체 이름 충돌 | 이름·권한·제약 충돌 0건, 적용 순서와 복구 절차 검토 완료 |
| G2 데이터 | 기존 25명과 등록 1건의 원본 건수/ID, 미연결 건수, 고아 FK | 기존 행 삭제·임의 병합 0건. 미연결 등록은 명시적 검토 상태 |
| G3 거래 | 중복 요청, 부분 실패, 수납 초과 배분, 취소/환불, 동시 저장 | 원자적 실패/재시도, 불변식 위반 0건, 감사 이력 확인 |
| G4 권한 | 역할별 접근, 로그인 만료, service role 경로, 닫힌 월 쓰기 | 비인가 쓰기와 우회 0건, 닫힌 월 수정 불가 |
| G5 성능 | 목록/검색, 저장 서버 확정, 월 집계의 호출 횟수·쿼리 시간·화면 반응 | 기존 측정값 대비 퇴행 없음. 목표 미달이면 원인을 기록하고 단계별 개선 |
| G6 대사 | 월별 원장 합계, 마감 스냅샷, Sheets 출력의 기간/버전/통화 | 건수·금액 일치, 재시도 중복 0건 |

G3~G6은 기능을 구현하고 격리된 시범 환경을 확보한 후 확인한다. 무료 요금제에서 유료 Supabase 브랜치나 별도 서비스를 선제 도입하지 않는다. 시범 환경의 선택은 요금과 데이터 격리 방식을 확인한 후 결정한다.

## 출시 및 복구

- 배포 전에는 운영 백업/복구 가능 범위와 복구 소요시간을 실제 요금제에서 확인한다. 개인정보가 있는 운영 DB를 로컬로 무단 복사하지 않는다.
- 각 M단계는 DB 객체 추가 → 서버의 읽기 호환 → 새 쓰기 제한적 활성화 → 지표/합계 확인 순으로 진행한다. 오래 실행되는 전체 테이블 변경이나 운영 부하 테스트는 피한다.
- 이상 발생 시 새 쓰기 경로를 중지하고 이전 화면/조회 경로로 복귀한다. 이미 확정한 재무 거래를 역방향 SQL이나 테이블 삭제로 취소하지 않는다. 정정 거래와 승인 이력을 사용한다.
- 실제 배포와 DB 이행은 별도의 검토 가능한 변경안과 적용 창을 준비한 뒤 수행한다. 현재 문서는 그 실행 명세의 기준선이다.
